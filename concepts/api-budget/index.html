    API budget¶

    Every call AlgoBridge makes to Salesforce counts against your org's API request limit. That is true of any integration you run yourself, and it shapes the whole design. This page explains the limit, how AlgoBridge keeps within it, and how to estimate what your instance will use.

    Why every call counts¶

    Salesforce limits how many API requests an org can make in a rolling 24 hours. An Enterprise Edition org gets 100,000 requests plus 1,000 per user licence. REST, SOAP, Bulk API and Bulk API 2.0 requests all count. Your other integrations share the same allowance.

    Some hosted sync services have calls that do not count toward your API request limits. That exemption is not open to software you run yourself. AlgoBridge pays for every call, the same as any other integration in your org, and in return you get no per-row charge and a sync that runs on your own infrastructure.

    So AlgoBridge treats call efficiency as a requirement, not a tuning option:

    • Never one call per record. Reads come in pages of 2,000 records, or as Bulk API jobs. Writes go 200 records per SOAP call, or as Bulk API jobs for large runs.
    • Cheap when nothing changes. A probe asks whether an object has changed before anything is read. See Salesforce to PostgreSQL.
    • The cheaper transport wins. Loads and sends compare the call cost of each transport and pick the lower one.
    • A governor watches the total. It slows and then pauses AlgoBridge before your org runs out.

    Watching usage at no cost¶

    Salesforce reports the org's current usage on every REST response, in the Sforce-Limit-Info header, and in the limit information returned with SOAP responses. AlgoBridge reads it from responses it was getting anyway, so tracking usage costs nothing. It also counts its own calls by the hour, so the connection screen can show the org's total use and AlgoBridge's share of it.

    The governor¶

    The governor compares the org's usage with two thresholds you set as instance settings.

    Org usage State What happens
    below the soft threshold normal Nothing changes.
    at or above soft (sf_api_soft_percent, default 70%) slowed Every mapping's poll interval is multiplied by 4, capped at one hour. The outbound maximum wait is multiplied by 4. The daily sweep is deferred. An API budget alert opens.
    at or above hard (sf_api_hard_percent, default 90%) paused Probes, fetches, writes to Salesforce and new Bulk jobs all wait. The alert escalates.
    back below soft minus 5 points normal Scheduling resumes and the alert closes.

    A few rules make the governor safe to rely on:

    • Capture never pauses. Changes in PostgreSQL keep queuing in the change log while writes are paused, so a pause costs latency, never data.
    • The 5-point margin stops flapping. Without it, an org sitting right on the threshold would open and close the alert on every pass.
    • Recovery is automatic. A paused instance moves back to slowed as soon as usage drops below the hard threshold. While paused, AlgoBridge refreshes its usage reading every 10 minutes, so it notices the drop.
    • It fails open. Before AlgoBridge has a usage reading, it runs normally rather than blocking.
    • Loads check headroom first. An initial load or Reload weighs its estimated cost against the remaining headroom before it starts.

    Choosing thresholds

    The thresholds are a share of the whole org's allowance, not of AlgoBridge's own use. If other integrations already use most of your limit, lower the soft threshold so AlgoBridge backs off before they are affected.

    Adaptive intervals¶

    Each mapping polls on its own interval, between a minimum (default 5 minutes, allowed 2 to 60) and a maximum (default 30 minutes). After 3 empty probes in a row the interval doubles. A change resets it to the minimum. A busy object stays near the minimum; a quiet one settles at the maximum and costs few calls. The console shows each mapping's current interval and why it last changed.

    What change detection costs¶

    The cost of finding changes depends on the change source. These figures are for 50 mapped objects.

    Change source Calls per poll Calls/day at a 2-minute interval Calls/day at 5 minutes Range across intervals
    One query per object (not used; for comparison) 50 36,000 — —
    Composite probe (default) 10 (5 objects per call) 7,200 about 2,900 about 480 to 7,200
    Apex probe 1 (up to 90 objects) 720 about 290 about 48 to 720
    Change notifier 0 per change — — about 25 a day: an hourly fallback poll plus 1 daily check

    On top of detection, each change source pays for:

    • Fetches. About 1 call per 2,000 changed records, and at least 1 call for each object a probe finds changed.
    • The daily check that your change source still works: 1 call a day.
    • The daily sweep. One Bulk query per mapping, about 5 calls per mapping per day.

    The Change notifier page breaks down its costs in full.

    Estimating your calls per day¶

    Add up five parts:

    Part How to estimate it
    Detection (objects ÷ objects per call, rounded up) × polls per day. Polls per day = 86,400 ÷ the interval in seconds.
    Fetch For each poll that finds changes: changed objects × (changed records ÷ 2,000, rounded up).
    Sweep 5 × mapped objects.
    Change-source check 1.
    Writes to Salesforce For each read-write mapping: changed rows ÷ 200, rounded up, per send. Each send is at least 1 call, and a mapping sends at most once per maximum wait (60 seconds by default) unless 200 changes are waiting. Runs of 2,000 or more go through Bulk API at about 6 calls each.

    One-off work, such as initial loads and Reloads, comes on top. A REST load costs about 1 call per 2,000 records. A Bulk load costs about 5 calls plus 1 per 50,000 records. AlgoBridge picks the cheaper one.

    Worked example¶

    The figures below are arithmetic from stated assumptions, not measurements.

    Assumptions. An Enterprise Edition org with 100 user licences, so the limit is 100,000 + 100 × 1,000 = 200,000 calls a day. 50 mapped objects on the Composite probe. All 50 stay busy enough to poll at the 5-minute minimum all day (the worst case for detection). Each poll finds changes in 10 objects, each with fewer than 2,000 changed records. 5 of the mappings are read-write, and each sends one SOAP batch a minute, around the clock.

    Part Arithmetic Calls/day
    Detection 10 calls per poll × 288 polls 2,880
    Fetch 10 objects × 1 call × 288 polls 2,880
    Sweep 5 × 50 250
    Change-source check 1
    Writes to Salesforce 5 mappings × 1,440 sends 7,200
    Total 13,211

    That is about 6.6% of the org's allowance, well under the 70% soft threshold.

    Two changes would cut it sharply. Installing the Apex bundle brings detection down from 2,880 to 288 calls. In practice, quiet objects back off toward the 30-minute maximum, so real detection and fetch costs are usually lower than this worst case.
