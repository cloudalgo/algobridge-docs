    The change notifier¶

    When a record is saved in Salesforce, a small Apex bundle tells your AlgoBridge instance which object changed. The instance then fetches the changed rows with one batched SOQL query and writes them to PostgreSQL. Learning about the change costs no Salesforce API calls, and an hourly fallback poll catches any notification that gets lost.

    This page explains how that works. To set it up, follow Install the Apex bundle. To compare the notifier with polling, see Change sources.

    When Step What happens
    Once Pair The operator clicks Pair. The org and the instance swap a signing key in 2 API calls.
    Once per object Add Flows A save Flow and a delete Flow are added for each notified object.
    Every save Notify The Flow queues a signed POST that carries object names only. This costs 0 API calls.
    Per burst of notifications Fetch One SOQL fetch per mapping pulls every row changed since the watermark into PostgreSQL.

    What gets installed in your org¶

    You deploy the bundle once from the Connections screen. Every name in it starts with algobridge_, so nothing in it can collide with anything else in your org.

    Resource Kind What it does
    algobridge_Status Apex REST Reports the bundle version, whether the org is paired, the endpoint, and who paired it. The console calls it after pairing and in the daily check.
    algobridge_ChangeProbe Apex REST Answers one question for many objects in a single call: has anything changed since this time? The fallback poll uses it, so 50 objects cost 1 call, not 50.
    algobridge_NotifierPair Apex REST Takes the one-time pairing code from the console, redeems it with the instance, and stores the key it receives.
    algobridge_NotifyChange Invocable action Called by the Flows. It removes duplicate object names, skips saves it should not report, checks the async limits, and queues the send. It catches every error, so it can never fail a user's save.
    algobridge_Notifier @future callout Signs the list of object names and posts it to the instance. It uses a 10-second timeout, never retries, never follows redirects, and presents a client certificate when one is configured.
    algobridge_Notifier__c Custom setting (hierarchy) Holds the instance endpoint, key id, signing secret, org id, the pairing user and an optional client certificate name. Only NotifierPair writes it.
    algobridge_Integration Permission set Grants the classes to the integration user that AlgoBridge connects as.
    algobridge_Instance Remote site setting Lets Apex call your instance's HTTPS host. It is set to your instance URL at deploy time.

    Each Apex class ships with its own test class.

    For every synced object, two record-triggered Flows call NotifyChange:

    Flow Runs Why
    algobridge_notify_<object>_<hash>_save After save Fires on create and update.
    algobridge_notify_<object>_<hash>_delete Before delete Fires on delete. It has to run before the delete, because the record no longer exists afterwards.

    The hash is six characters derived from the object's API name. It keeps long names unique within Salesforce's 80-character limit for Flow names.

    Adding the Flows

    Today you add the Flows by hand, following the recipe in Install the Apex bundle. A coming release adds a background job that deploys and removes them for you. It is described below.

    Pairing: one click, two calls¶

    Open the pairing sequence full size

    1. The console opens a pairing slot. Clicking Pair writes a one-time code to AlgoBridge's database. If the round trip hasn't finished within 3 minutes, the code stops working.
    2. The console calls the org once. It sends POST /services/apexrest/algobridge/v1/notifier/pair with the code and the instance's notify URL, plus the client certificate name when mutual TLS is on. This is the first of the two Salesforce calls.
    3. Apex calls the instance back. NotifierPair sends {code, orgId, apexVersion} to /notify/v1/pair. The instance redeems the code once, generates a key, encrypts the secret with AES-GCM, pins the key to the org id, and returns {keyId, secret, notifyUrl}.
    4. Apex stores the key and answers. The key goes into algobridge_Notifier__c with the user who paired. The console receives {paired, keyId, pairedBy}, and one status call confirms it. That is the second Salesforce call.

    Why the org calls the instance

    The secret never passes through your browser or clipboard, and the instance learns the org id from the org itself. Pairing again rotates the key, and the old key stops working straight away.

    A record save, end to end¶

    Open the save sequence full size

    1. The Flow fires inside the user's transaction. The save Flow or the delete Flow calls algobridge_NotifyChange.notify, passing only the object name. Record data never leaves the org on this path.

    2. NotifyChange decides whether to send. It skips the send when:

      • the save came from the integration user. That is AlgoBridge writing PostgreSQL changes back, and reporting it would echo the change.
      • the org isn't paired.
      • the code is already running in a future or batch context, where Salesforce doesn't allow another @future call.
      • the transaction has used up its future-call limit.
      • the org is within the last 1% of its daily async Apex allowance. That last 1% is left for your own automation.

      Otherwise it queues one @future call per transaction, carrying the object names with duplicates removed. It catches every exception, so the save always commits. 3. Notifier signs and posts after the commit. The callout builds the body and signs it with HMAC-SHA256 over a canonical string. The request has a 10-second timeout and is never retried or redirected. 4. The instance checks the request, cheapest check first. The first check that fails rejects the request, so the expensive checks run only once the cheap ones have passed. 5. One fetch per mapping. For each mapping on a named object, the instance queues one sf-fetch job and answers {accepted, ignored}. Only one fetch job per mapping can be waiting at a time. A bulk load of 10,000 records sends many notifications, but they collapse into a single fetch. 6. SOQL since the watermark, then upsert. The fetch runs under the API budget governor. It reads every row changed since the mapping's watermark in REST query pages, and applies them 500 rows at a time. It upserts the rows into your PostgreSQL by sfid, then moves the watermark forward.

    POST /notify/v1/changes
AlgoBridge-Key-Id:    <key id>
AlgoBridge-Org:       <18-character org id>
AlgoBridge-Timestamp: <unix seconds>
AlgoBridge-Nonce:     <random>
AlgoBridge-Signature: v1=<hex>

    The checks on /notify/v1/changes¶

    Order Check What it stops
    1 The body is at most 16 KB and is valid JSON Oversized or garbage payloads, before any lookup
    2 The key id is known and active Strangers and rotated keys
    3 The timestamp is within 5 minutes of the instance's clock Captured requests replayed later
    4 The signature matches, compared in constant time Forged or altered requests, and timing probes
    5 The org header matches the key's org and the connected org A key copied into another org
    6 The nonce hasn't been seen in the last 10 minutes Replays inside the time window
    7 The body lists 1 to 200 object names Malformed bodies
    8 At most 60 requests a minute per key Floods from a misbehaving org

    Safety nets¶

    A notification is a hint to fetch now, not the data itself. If one is lost, the sync is delayed but never wrong, because each of these nets catches up on its own.

    What happens What catches it Cost
    The instance is down, or a callout times out The hourly fallback poll. It runs on the hour, so all notified mappings share one ChangeProbe call and fetch only the objects that changed. The interval is sf_notifier_fallback_seconds, 3600 by default. 1 call an hour
    An admin deactivates or deletes one of the Flows The daily check: one status call and one Flow listing. Drift shows on the mapping's chip. AlgoBridge never turns a Flow back on against an admin's decision. 2 calls a day
    The key is rotated, or the org is paired somewhere else Requests signed with the old key fail check 2 and are refused. The fallback poll keeps data flowing until the org is paired again. 0
    The org is close to its daily async Apex allowance NotifyChange stops queueing at the 1% reserve, and the fallback poll takes over. 0
    A delete or an edit slips past everything The nightly reconciliation sweep compares ids and catches it. Already budgeted

    What change detection costs¶

    AlgoBridge counts against your org's daily API limit, so every way of detecting changes has a price in calls per day. These figures are for 50 synced objects. Fetching the changed rows costs the same whichever way a change was detected, so it isn't included.

    Detection How Calls a day
    Composite polling Ask every object for changes on the adaptive interval about 480 to 7,200
    Apex probe polling One ChangeProbe call covers all 50 objects about 48 to 720
    Notifier Saves push object names, plus the hourly fallback probe and the daily check 0 + 24 + 2
    One-off setup Pairing (2 calls), and the Flow deploy once the Flows job ships (at most 8 per object) up to 402, once

    Planned: the Flows job¶

    Coming in a later release

    This section describes behaviour that is still being built. It may change before release.

    Open the Flows job diagram full size

    Whenever a mapping is turned on or off, or the notifier is paired, a background job runs for each affected object. Only one job runs per object at a time, so two triggers for the same object never race. Each run:

    1. Plans. It lists the object's existing Flows (1 call). It wants a Flow pair if the mapping is on, and nothing if it is off.
    2. Retires a hand-made Flow. It deactivates any Flow added by hand from the recipe, so the object doesn't notify twice (up to 2 calls).
    3. Deploys or removes the pair. It makes one Metadata API deploy and polls it about 3 times. When the mapping is off, the same step removes the Flows and the chip reads removed.
    4. Reads back and activates. It reads what was deployed (1 call) and switches on any of its Flows that are still inactive (up to 2 calls). If the org refuses, the chip reads inactive · activate in Setup and the job doesn't fail.

    That is at most 8 calls per object, spent once. For 50 objects that is at most 400 calls, and the governor spreads them out. While the governor has paused spending, the job waits and runs later. A configuration problem, such as a missing permission, marks the job failed without retrying. A temporary failure retries. Either way, the mapping keeps syncing on the hourly fallback poll.

    Planned: hardening the notify endpoint¶

    Two optional layers are planned for locked-down deployments. Both sit on top of the request signature, and neither replaces it.

    Mutual TLS
    You upload a client certificate to Salesforce and name it during pairing. The Notifier presents it on every send. Your reverse proxy verifies the certificate and forwards its fingerprint in a header. AlgoBridge trusts that header only on requests that come from an address in TRUSTED_PROXIES, so a client can't forge it by sending the header itself.
    Source allow-list
    You choose a verified source: a list of Salesforce egress address ranges. AlgoBridge refuses requests from any other address.
