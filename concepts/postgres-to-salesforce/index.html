    PostgreSQL to Salesforce¶

    This page explains how a row you insert, update or delete in PostgreSQL reaches Salesforce. It applies to mappings set to read-write. Read-only mappings never write to Salesforce.

    The path has four steps:

    1. Capture. A trigger on your table records the change in a log, inside your own transaction.
    2. Batch. Changes wait briefly so they can be sent together.
    3. Send. A batch goes to Salesforce over SOAP or Bulk API v2, whichever costs fewer calls.
    4. Write back. Salesforce's answer, including the new record Id, is written to your row.

    Open the PostgreSQL to Salesforce data flow full size

    Capture: a trigger and a change log¶

    When you activate a read-write mapping, AlgoBridge adds a trigger named algobridge_capture to its table. The trigger runs before every insert, update and delete, for each row. It writes the row's old and new values, as hstore, to algobridge_change_log, and it sets the row's algobridge_lastop column to PENDING.

    Because the trigger runs inside your transaction, capture is exact. A change is logged only if your transaction commits, and a rollback leaves nothing behind. Your application keeps writing plain SQL. It needs no client library and makes no API call.

    Capture never stops. Even when the API budget governor pauses sending, the trigger keeps logging, so nothing is lost while Salesforce is out of reach.

    What the trigger cannot see

    A trigger captures only the writes that fire it. Three things bypass it, and changes made that way never reach Salesforce:

    • TRUNCATE, which fires no row trigger. Use DELETE when you want removals to reach Salesforce.
    • Disabling the trigger with ALTER TABLE … DISABLE TRIGGER.
    • A session with session_replication_role = replica, which skips ordinary triggers.

    Batching: size and maximum wait¶

    Sending one change per API call would quickly exhaust your org's limits. So AlgoBridge waits for changes to accumulate, within a bound you control.

    Every mapping checks its queue on a tick of about 10 seconds. The check reads PostgreSQL only and costs no Salesforce call. A send starts when either of these is true:

    • 200 changes are waiting. That fills one SOAP call.
    • The oldest change has waited longer than the maximum wait. The default is 60 seconds, adjustable from 10 to 900 seconds with outbound_max_wait_seconds.

    So a busy table sends full batches quickly, and a quiet table sends a single change within about a minute. While the governor has slowed the instance, the maximum wait is multiplied by 4.

    A send claims up to 10,000 waiting changes at once. Claims use SKIP LOCKED, so two workers never take the same row. Within a mapping, changes are claimed strictly in capture order.

    Choosing the transport: SOAP or Bulk API v2¶

    AlgoBridge picks the transport by estimated call cost.

    SOAP Bulk API v2
    Records per call up to 200 a job, any size
    Cost 1 call per 200 records about 6 calls per job
    Used when runs under 2,000 records, and always for Merged writes runs of 2,000 or more of the same action, Ordered writes only
    Answers at once asynchronously

    A Bulk job's fixed overhead makes it more expensive than SOAP below about 1,200 records. Switching at 2,000 leaves a clear margin. A Bulk insert also needs the mapping's External ID field so results can be matched back to rows. Without one, the run simply stays on SOAP.

    Updates send only the fields that changed. A field you set to NULL is sent as a cleared field. Inserts send every writable field.

    Ordered and Merged writes¶

    The instance's write algorithm controls how several changes to the same record are sent.

    Ordered (default) Merged
    Several changes to one record Sent one by one, in order Folded before sending: an insert plus updates becomes one insert, several updates become one update with the latest values
    Transport SOAP, or Bulk for large runs SOAP only

    Ordered is the safe choice for most installs. Merged saves calls when the same records are updated many times between sends.

    Parents before children¶

    If a row refers to a parent record that has not reached Salesforce yet, the row is held back until the parent is inserted. Only that record and its children wait; everything else keeps syncing, where some sync tools stop the whole queue behind one failed insert.

    Write-back and echo suppression¶

    The Salesforce call runs between two short database transactions, so no lock on your table is held while AlgoBridge waits on the network.

    When Salesforce answers, AlgoBridge writes back to each row: the new sfid for an insert, the system fields, and the sync state in algobridge_lastop and algobridge_err. The sent changes move to algobridge_change_log_archive in the same transaction. They stay there for 30 days for the Activity screen.

    The write-back runs under SET LOCAL ab.in_sync = true. The capture trigger sees that setting and does not log these writes. Without it, writing the sfid back would itself look like a new change and be sent again. The setting is local to the transaction, so your own sessions are never affected.

    When Salesforce says no¶

    Each change in the log has a state.

    State Meaning
    NEW Waiting to be sent.
    CLAIMED Taken by a send in progress.
    DONE Accepted by Salesforce.
    MERGED Folded into another change by Merged writes.
    DEAD Failed for good; needs your decision.
    DISCARDED You chose to drop it.

    Transient failures are retried¶

    A rejection from Salesforce is always retried, because it is often temporary: a locked record, a validation rule someone is about to fix, or a missing parent. Each change gets 5 attempts. The delay grows from 60 seconds and doubles each time, capped at one hour, with random jitter so retries do not arrive in step. A change that keeps failing reaches DEAD after about 15 minutes.

    If a worker stops in the middle of a send, its claimed changes return to NEW after 21 minutes and are sent again. Inserts go as upserts on the External ID where the mapping has one, so a resent insert updates the record the first attempt created instead of making a duplicate.

    Permanent failures stop at once¶

    Some changes can never be sent, whatever Salesforce says. An example is a row whose value cannot be converted to the field's type. AlgoBridge marks these DEAD straight away rather than wasting calls on retries.

    Dead changes stay visible¶

    A DEAD change stays in the live log. It is not silently dropped. On the Activity screen you can retry or discard one change, or retry every failed change at once.

    Error text never reaches the logs

    Salesforce's error messages can quote the field values you sent. AlgoBridge stores the error with the change and shows it only on the Activity screen, behind sign-in. It never writes it to a log line.

    See Mappings to make a mapping read-write, and Live log to watch sends as they happen.
