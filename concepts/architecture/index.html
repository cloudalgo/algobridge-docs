    Architecture¶

    AlgoBridge is one container image. It talks to two PostgreSQL databases and one Salesforce org. It has no message broker, no cache and no shared disk. This page explains how those parts fit together and why the design is so small.

    Open the architecture diagram full size

    One instance, one sync pair¶

    An instance syncs exactly one Salesforce org with exactly one client PostgreSQL database. There are no workspaces and no tenants. If you need to sync a second org or a second database, run a second instance.

    This keeps the product easy to reason about. Every setting, every job and every alert on an instance belongs to the same pair, and you never have to ask which connection a row belongs to.

    One image, three roles¶

    The same image runs in any of three roles. You choose the role with the APP_ROLE environment variable.

    APP_ROLE Serves the console Runs sync jobs Typical use
    all (default) yes yes A single container. Good for most installs.
    web yes no Scale the console separately from the sync work.
    worker no yes Run sync work away from the public endpoint.

    A fourth mode applies the database migrations and exits. Run it with docker run <image> migrate, or set MIGRATE_ON_BOOT=true to have the container migrate before it starts. A web or worker process refuses to boot against a database whose schema is behind its build. It tells you to run the migration first instead of starting in a broken state.

    Each process exposes /healthz (the process is alive) and /readyz (it can reach its database and is ready for traffic).

    See Workers and jobs for running several workers.

    All coordination happens in PostgreSQL¶

    AlgoBridge has no Redis, no message broker and no external queue. Jobs, locks, schedules and the worker registry all live in PostgreSQL. The job engine keeps its tables in the algobridge_jobs schema of AlgoBridge's own database. No process holds coordination state in memory.

    This has three practical results:

    • Nothing extra to run. You operate PostgreSQL and a container. There is no second stateful service to back up, patch or monitor.
    • Workers are interchangeable. Any worker can pick up any job. If a worker dies, another one takes over its work in about 20 seconds.
    • Restarts are safe. On a normal stop, a worker finishes in-flight work for up to 30 seconds before it exits. Give your container runtime a stop grace period of 45 seconds so the drain can complete.

    Each mapping runs on a short self-rescheduling tick of about 10 seconds. A watchdog checks every minute and restarts any mapping whose tick chain has broken. A tick that fails 5 times in a row is set aside as a dead job, so it cannot loop forever.

    Two databases, two owners¶

    AlgoBridge uses two PostgreSQL databases. They must be different databases. They may share a server.

    AlgoBridge's own database Your client database
    Owned by AlgoBridge You
    Set by DATABASE_URL the console, or CLIENT_DATABASE_URL
    Holds users and sessions, the Salesforce connection, mappings, jobs and the worker registry, sync runs, alerts, idempotency keys, instance settings, poll watermarks, notifier keys your mapped tables and the small set of objects AlgoBridge needs to capture your changes
    Schema changes migrations shipped with each release only additive changes you approve in the console

    The split exists so that AlgoBridge's bookkeeping never mixes with your data. You can grant AlgoBridge narrow rights on your database, back the two up on different schedules, and remove AlgoBridge without leaving product tables among your own.

    AlgoBridge enforces the split. It refuses to use its own database as the client database, and the migration refuses to run against a database that already holds AlgoBridge's change log. No transaction ever spans both databases.

    What AlgoBridge adds to your database¶

    Everything AlgoBridge creates in your database lives in one schema, algobridge by default, and carries the algobridge_ prefix. The prefix keeps its objects distinct from yours and from any other sync tool on the same database.

    Object Purpose
    Your mapped tables One table per mapped Salesforce object, with a unique index on sfid and, where you choose one, on the External ID column.
    hstore extension Stores each captured change as old and new key-value pairs.
    algobridge_change_log The queue of changes waiting to go to Salesforce.
    algobridge_change_log_archive Sent changes, kept for 30 days for the Activity screen.
    algobridge_capture_change() and the algobridge_capture trigger Records every insert, update and delete on a read-write table.
    algobridge_lastop, algobridge_err, algobridge_id columns On read-write tables only: the row's last sync state, its last error, and a stable row identity.

    Read-only mappings get no trigger and no status columns.

    Schema changes are additive only

    AlgoBridge never drops or recreates one of your tables. It adds columns and indexes; it never narrows a column type. When you remove a field from a mapping, its column stays. Every change is shown to you as a diff and runs only when you press Apply. Before it runs, a preflight check names any database grant that is missing. See Client database.

    TRUNCATE is not captured

    Row triggers do not fire on TRUNCATE, so a truncated table is not synced to Salesforce. Use DELETE when you want removals to reach Salesforce.

    Runs anywhere a container runs¶

    AlgoBridge is built to be provider-agnostic. It needs three things:

    1. A long-lived container runtime.
    2. PostgreSQL 15 or later.
    3. Outbound HTTPS to Salesforce.

    Beyond that it makes no assumptions about where it runs:

    • Secrets arrive as environment variables.
    • All state lives in PostgreSQL, so the container needs no local disk.
    • Logs go to standard output.
    • TLS ends at your reverse proxy or load balancer.
    • Sign-in is local accounts or any OpenID Connect provider.
    • Email, when you want it, is plain SMTP.
    • The application code calls no cloud-provider SDK.

    The image is built for more than one CPU architecture.

    Scale-to-zero platforms

    AlgoBridge runs scheduled work, so it must stay running. On a platform that scales idle containers to zero, set the minimum instance count to at least 1.
