    Salesforce to PostgreSQL¶

    This page explains how a change made in Salesforce reaches your PostgreSQL table. Each mapped object goes through the same three steps:

    1. Detect. Find out cheaply whether the object has changed since the last pass.
    2. Fetch. Read only the changed records, in large pages.
    3. Apply. Write them to your table in one transaction, matched on sfid.

    AlgoBridge detects changes by polling with SOQL, or by being told about them by the optional change notifier. It does not use Salesforce Change Data Capture or streaming events.

    Why polling, and why it is cheap¶

    Every call AlgoBridge makes counts against your org's daily API limit (see API budget). So the design goal is simple: never spend a call per record, and spend as few calls as possible when nothing has changed. In most orgs, most objects are unchanged most of the time. A cheap "has anything changed?" check, followed by a full read only when the answer is yes, uses far fewer calls than reading every object on a timer.

    Watermarks¶

    AlgoBridge keeps a watermark for each mapping in its own database. The watermark is the SystemModstamp of the newest record it has applied. Every detect and fetch asks for records at or after that stamp.

    The watermark is deliberately cautious:

    • It only moves after the apply commits. It advances to the highest stamp actually written to your table. A crash mid-fetch repeats some work; it never skips a record.
    • It uses >=, not >. SOQL timestamps have one-second resolution, so several records can share a stamp. Re-reading the boundary second is cheap and safe, because the apply is idempotent.
    • It stays 120 seconds behind the present. A record saved in a long Salesforce transaction can appear with a stamp slightly in the past. Holding the watermark back by two minutes keeps such records from being missed.
    • A long gap triggers a full fetch. If a watermark is more than 14 days old, AlgoBridge treats the mapping as out of date and fetches it in full. Salesforce keeps deleted records in the recycle bin for 15 days, so a shorter gap still sees every deletion.

    Detecting changes: probes¶

    A probe asks one question per object: has any record changed since the watermark? A singleton probe job runs once a minute and checks every mapping that is due. You choose how the probe is answered. This choice is the instance's change source.

    Change source How it asks Objects per call Needs
    Composite (default) One queryAll of SELECT Id … WHERE SystemModstamp >= <watermark> LIMIT 1 per object, bundled into one Composite request 5 nothing extra
    Apex probe One call to the AlgoBridge Apex class, which runs the same check for each object inside Salesforce 90 the Apex bundle installed in the org
    Change notifier Salesforce posts the names of changed objects to AlgoBridge 0 per change the Apex bundle, Flows on each object, and a reachable AlgoBridge URL

    The Composite probe uses queryAll so that deleted records count as changes too.

    The Apex probe class is read-only. It runs with sharing and in user mode, so it sees only what the integration user may see. It never returns record data, only which objects have changed.

    Choosing and keeping a change source¶

    You pick the change source on the console. AlgoBridge checks that the source works, with one status call, before it saves your choice. After that it re-checks once a day at 02:20 UTC, at a cost of 1 call.

    If your chosen source stops working, for example because someone removed the Apex class, AlgoBridge falls back to the next one that still works. The notifier falls back to the Apex probe if it is verified, and otherwise to Composite. At the same time it opens an alert. Your selection is never changed for you. Once you fix the cause, the next check restores your chosen source. See Change sources.

    The change notifier, in short¶

    With the notifier, two record-triggered Flows on each object call an Apex action when a record is saved. The action sends AlgoBridge one signed POST /notify/v1/changes naming the objects that changed. It never sends record data. Salesforce's outbound callouts do not count as API requests, so detection costs nothing per change. AlgoBridge then fetches the changes as usual.

    The notifier is a fast path, not the only path. Flows do not fire in every case (undelete and merge, for example). A slow fallback poll, hourly by default, and the daily sweep catch anything a notification missed. The Change notifier page covers pairing, the request checks, the safety nets and the costs in full.

    Adaptive intervals¶

    Each mapping has its own probe interval, and AlgoBridge adjusts it to how busy the object is:

    • It starts at the minimum interval: 300 seconds by default, adjustable from 120 to 3600 seconds.
    • After 3 empty probes in a row, the interval doubles, up to the maximum interval (1800 seconds by default).
    • As soon as a probe finds a change, the interval drops back to the minimum.
    • If Salesforce rejects one object's probe, only that mapping backs off. The others in the same call carry on.

    A busy object is checked often. A quiet one costs a few calls an hour. When the API budget governor slows the instance down, all intervals stretch further.

    Fetching changed records¶

    When a probe reports a change, AlgoBridge reads the changed records with one queryAll. The query selects the mapped fields plus IsDeleted, ordered by SystemModstamp ascending. Salesforce returns up to 2,000 records per page, and each page is one API call. Records are applied in batches of 500.

    Formula fields are never synced. Their values change without changing SystemModstamp, so polling could never keep them correct. Leaving them out is more honest than syncing values that silently go stale.

    Applying records: upsert on sfid¶

    Each batch is applied to your table in one transaction:

    1. Deletes first. Records Salesforce reports as deleted are removed by sfid.
    2. Match on External ID. If the mapping has an External ID field, a row with the same External ID and no sfid yet is updated and gains its sfid. This links rows you inserted in PostgreSQL before Salesforce assigned an Id.
    3. Upsert on sfid. Every live record is then inserted, or updated where a row with the same Salesforce Id already exists.

    If one row cannot be written, for example because a value breaks one of your constraints, that row is skipped and counted. The rest of the batch still commits. One bad row never blocks a whole object.

    Echo suppression¶

    The apply runs under SET LOCAL ab.in_sync = true. The capture trigger on your table sees that setting and does not record these writes as new changes. Without it, every record AlgoBridge pulled from Salesforce would be sent straight back. The setting is local to the transaction, so it can never leak into your own sessions.

    When a record has also changed on the PostgreSQL side, the apply follows the mapping's conflict policy.

    Initial load, reload and the daily sweep¶

    Polling handles day-to-day changes. Three other jobs keep a table complete:

    • Initial load. When you activate a mapping, AlgoBridge counts the records and loads them all. It picks whichever transport costs fewer calls: REST queries at about one call per 2,000 records, or a Bulk API query at about 5 calls plus one per 50,000 records. When the load ends, the watermark is set to the moment it started, so changes made during the load are picked up next.
    • Reload. Empties the table and loads it again from Salesforce. Because it erases data, you confirm it by typing the table name.
    • Daily reconciliation sweep. Once a day, by default at 03:00 UTC, one Bulk query reads every mapped field of every record, at about 5 calls per mapping. The sweep removes rows Salesforce no longer has and fixes rows that differ, with Salesforce's value winning. It catches what polling cannot, such as records purged from the recycle bin before a poll saw them. It skips rows with a change still waiting to go out, and it refuses to delete a large share of a table at once. It waits while the governor has slowed or paused the instance.

    See Mappings for activating, reloading and sweeping a mapping, and Live log to watch these passes as they run.
