    Install the Apex bundle¶

    This guide installs the AlgoBridge Apex bundle in your org, which the Apex probe and the change notifier need. It then pairs the change notifier, adds the Flows that drive it, and checks that it works.

    For how the notifier signs and checks each request, see How the change notifier works.

    What the bundle contains¶

    The bundle is plain metadata, not a managed package, so you can read every line before you deploy it. Its source is in packages/salesforce/apex in the repository.

    Component Purpose
    algobridge_ChangeProbe The Apex probe. Read-only: reports, for up to 90 objects, whether each one changed.
    algobridge_Status Reports the bundle version and which features are enabled.
    algobridge_NotifierPair Receives the one-time pairing from AlgoBridge.
    algobridge_NotifyChange The Flow action AlgoBridge: Notify Change.
    algobridge_Notifier Sends the signed notification to AlgoBridge.
    algobridge_Notifier__c Hierarchy custom setting that holds the notifier key.
    algobridge_Instance Remote site setting for your AlgoBridge address.
    algobridge_Integration Permission set AlgoBridge Integration.
    Five test classes One per class above.

    The bundle is version 1.1.0. A bundle older than 1.1.0 has no notifier, and the console disables Pair notifier until you deploy again.

    Before you start¶

    • Salesforce is connected.
    • The integration user has Modify All Data, or Modify Metadata Through Metadata API Functions, and Author Apex. These are needed to deploy from the console.
    • For the change notifier: PUBLIC_URL is an https:// address that Salesforce can reach.

    Step 1: Deploy the bundle¶

    1. Open Instance → Connections → Change detection.
    2. Click Deploy bundle.

    The deploy runs in the background and the panel shows Deploying…, then Deploy succeeded or Deploy failed. It runs only the bundle's five test classes, and it writes the origin of your PUBLIC_URL into the remote site setting for you.

    It costs one Metadata API deploy, its status polls, and one status call.

    1. Edit the remote site setting in force-app so its URL is your PUBLIC_URL origin. It ships as the placeholder https://instance.invalid. Don't commit your edit. You can also change it after the deploy in Setup → Remote Site Settings.

    2. Deploy, running only the bundle's tests:

      cd packages/salesforce/apex
sf project deploy start \
  --source-dir force-app \
  --target-org <your-org-alias> \
  --test-level RunSpecifiedTests \
  --tests algobridge_ChangeProbe_Test \
  --tests algobridge_Status_Test \
  --tests algobridge_NotifyChange_Test \
  --tests algobridge_Notifier_Test \
  --tests algobridge_NotifierPair_Test

    Note

    If PUBLIC_URL changes later, deploy the bundle again and pair the notifier again, so the remote site and the key match the new address.

    Step 2: Assign the permission set¶

    The deploy doesn't assign the permission set.

    1. In Salesforce, open Setup → Permission Sets → AlgoBridge Integration.
    2. Click Manage Assignments and assign it to the integration user only.

    The probe runs with sharing, in user mode, so it sees only what the integration user can read.

    Step 3: Verify¶

    To use the Apex probe, click Use this source on the Apex probe card. AlgoBridge makes one status call and saves the source only if the bundle reports the expected version with the probe enabled. The card then shows Verified and the time.

    If you only want the Apex probe, you're done. Continue to pair the change notifier.

    Pair the change notifier¶

    Pairing gives the org a key it uses to sign notifications, and gives AlgoBridge a way to check them.

    1. Confirm the bundle is 1.1.0 with the remote site set to your PUBLIC_URL, and that the permission set is assigned.
    2. On the Change notifier card, click Pair notifier.

    AlgoBridge sends the org a single-use code that expires in 10 minutes and is never shown. Salesforce calls AlgoBridge back once to collect the key. This costs two API requests, the pairing and a status check. You see Notifier paired. and the card shows Paired, key abk_…, no notification yet.

    Add the Flows¶

    The notifier is driven by two record-triggered Flows on each synced object. Add them by hand for every object you map.

    Flow 1: saves

    1. In Setup → Flows, create a Record-Triggered Flow on the object.
    2. Trigger it when A record is created or updated, with no entry conditions.
    3. Optimize it for Actions and Related Records.
    4. Add an Action and pick AlgoBridge: Notify Change (category AlgoBridge).
    5. Set its input records to {!$Record}.
    6. Save it with the label AlgoBridge notify <Object> save and the API name algobridge_notify_<Object>_save.
    7. Activate it.

    Flow 2: deletes

    Repeat the steps with the trigger A record is deleted, the label AlgoBridge notify <Object> delete and the API name algobridge_notify_<Object>_delete.

    API names for custom objects

    Flow API names can't contain a double underscore, so write Invoice__c as Invoice_c: algobridge_notify_Invoice_c_save.

    A Flow on an object you don't sync is harmless: AlgoBridge ignores the notification. Object names match regardless of case.

    Select the change notifier¶

    1. Click Use this source on the Change notifier card.
    2. AlgoBridge checks the notifier is installed and paired, that PUBLIC_URL uses https, and that it holds a live key.
    3. Save a record on a synced object in Salesforce. The card's last notification time updates and the change arrives in PostgreSQL.

    You can watch notifier_notification_accepted events in the Live log.

    Rotate or revoke the key¶

    • Rotate key issues a new key for two API requests. The old key keeps working for 24 hours, so in-flight notifications aren't lost. Rotate on a schedule.
    • Revoke deletes every key, with no API request. Salesforce keeps sending, and each send is refused until you pair again. Sync falls back to polling. Repeated refusals open the notifier_auth_failures alert.

    If a key may have leaked

    Click Revoke, then Pair notifier. Don't use Rotate key: it keeps the old key working for 24 hours.

    Disconnecting Salesforce deletes the keys, so pair again after you connect. A reconnect to the same org keeps them.

    Know the limits¶

    • Saves by the integration user aren't notified. If you reconnect as a different user, pair again.
    • Undelete, merge, cascade delete and deactivated Flows send nothing. The hourly fallback poll and the daily reconciliation sweep catch these.
    • Nothing is sent from batch or future contexts.
    • Each notification is one asynchronous Apex call, from the org's daily allowance and from the transaction's limit of 50 future calls, which your own code shares. The action skips sending when less than 1% of the daily allowance is left.
    • Sends are fire and forget with a 10 second timeout. A missed send is caught by the fallback poll.

    Remove the bundle¶

    1. Deactivate and delete the AlgoBridge Flows.
    2. Click Revoke on the Change notifier card.
    3. Switch the change source to Composite polling.
    4. In Salesforce, delete the bundle's classes, the custom setting, the remote site setting and the permission set.

    If you skip step 3, the daily check marks the source unavailable and polling falls back to Composite.

    Troubleshooting¶

    Deploy failed

    The panel shows the deploy error. The usual causes are a missing Author Apex or Modify Metadata permission on the integration user, or a failing test in the org. Fix the cause and click Deploy bundle again.

    A bundle deploy is already running.

    A deploy is in progress. Wait for it to finish.

    The Apex bundle in the org has no notifier.

    The org has a bundle older than 1.1.0. Deploy the bundle, then pair again.

    Salesforce refused the pairing.

    The AlgoBridge Integration permission set isn't assigned to the integration user, or the remote site setting doesn't cover your PUBLIC_URL. Pairing is also limited to 5 attempts a minute: if you hit the limit, wait a minute. Nothing changed, so fix the cause and pair again.

    Notifier paired, but the follow-up status check found a problem.

    The pairing worked but the status call found an issue. The Change notifier card shows it once the notifier is the selected source, and selecting it checks again.

    Notifications stop arriving

    Check that the Flows are active, that PUBLIC_URL and the remote site still match, and look for notifier_notification_rejected in the Live log. If the log reports notifier_key_unreadable, pair again.
