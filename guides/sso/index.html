    Set up sign-in¶

    This guide sets up how people sign in to the console: AlgoBridge passwords with optional two-step verification, single sign-on through Google Workspace, Microsoft Entra ID, or any standard OpenID Connect provider, or a mix of them.

    Sign-in is configured with environment variables, so each change needs a restart.

    Before you start¶

    • PUBLIC_URL is set to the address people use, for example https://sync.example.com. Redirect URIs are built from it.
    • At least one admin exists. See Create the first admin.
    • For SSO: admin access to your identity provider, so you can register an application.

    How the settings fit together¶

    Variable What it does
    AUTH_PROVIDERS Comma-separated list of sign-in methods: local, google, microsoft, oidc. For example local,google. Each SSO provider listed gets its own button.
    AUTH_LOCAL_LOGIN Who may sign in with an AlgoBridge password: all (the default), admins or off.
    AUTH_ALLOWED_DOMAINS Optional. Email domains allowed to sign up on their first SSO sign-in, without an invite.

    Rules that AlgoBridge checks at startup:

    • local must be in AUTH_PROVIDERS unless AUTH_LOCAL_LOGIN=off.
    • AUTH_LOCAL_LOGIN=off needs at least one SSO provider.
    • Each SSO provider's variables are required together. A deployment missing any of them refuses to start, so a half-configured provider can't go live.

    Local passwords and two-step verification¶

    Local sign-in is on by default. Passwords are hashed with argon2id. There is no self-service "forgot password": an admin issues a set-password link from the Users page.

    Two-step verification is optional and applies to local passwords only. It needs ENCRYPTION_KEY set, because the authenticator key is stored encrypted. Each person turns it on for themselves:

    1. Click your name at the top of the console to open Account.
    2. Under Two-step verification, click Set up.
    3. Scan the QR code with an authenticator app, or enter the key by hand. The key is shown once.
    4. Enter the 6-digit code the app shows and click Turn on.

    From then on, signing in asks for a code after the password. If someone loses their authenticator, an admin can turn two-step verification off for them on the Users page.

    Add a single sign-on provider¶

    The redirect URI for each provider is PUBLIC_URL followed by /auth/callback/<provider>. It must match exactly.

    Google sign-in accepts accounts from one Google Workspace domain.

    1. In the Google Cloud console, open APIs & Services → OAuth consent screen and set User type to Internal. This limits sign-in to your Workspace organization before AlgoBridge sees a login.
    2. Open APIs & Services → Credentials → Create credentials → OAuth client ID.
    3. Choose Application type: Web application.

    4. Under Authorized redirect URIs, add:

      https://sync.example.com/auth/callback/google

    5. Save, and copy the Client ID and Client secret.

    6. Set these variables and restart:

      AUTH_PROVIDERS=local,google
GOOGLE_CLIENT_ID=change-me
GOOGLE_CLIENT_SECRET=change-me
GOOGLE_HOSTED_DOMAIN=example.com

    AlgoBridge checks Google's hosted-domain (hd) claim on every sign-in and accepts only GOOGLE_HOSTED_DOMAIN. Personal Gmail accounts never carry it, so they're always refused.

    Microsoft sign-in accepts accounts from one Entra ID tenant.

    1. In the Entra admin center, open Identity → Applications → App registrations → New registration.
    2. Choose Accounts in this organizational directory only (Single tenant).

    3. Under Redirect URI, choose platform Web and enter:

      https://sync.example.com/auth/callback/microsoft

    4. Open Certificates & secrets → New client secret. Copy the value, which is shown once, and note its expiry date. Rotate it before it expires, or sign-in stops working.

    5. From the app's Overview, copy the Application (client) ID and the Directory (tenant) ID.
    6. Open Token configuration → Add optional claim, choose token type ID, and add email and xms_edov.

    7. Set these variables and restart:

      AUTH_PROVIDERS=local,microsoft
MICROSOFT_CLIENT_ID=change-me
MICROSOFT_CLIENT_SECRET=change-me
MICROSOFT_TENANT_ID=00000000-0000-0000-0000-000000000000

    MICROSOFT_TENANT_ID must be your tenant's GUID. common, organizations and consumers are refused at startup, because they would admit accounts from any tenant.

    Don't skip the optional claims

    Entra's email claim alone isn't guaranteed to be verified. AlgoBridge trusts it only with xms_edov: true. Without both claims, an invited user's first Microsoft sign-in is refused, because there is no verified email to match the invite.

    Use this for Okta, Keycloak, Auth0 or any other standard OpenID Connect provider. The provider must support:

    • discovery at <issuer>/.well-known/openid-configuration,
    • the authorization code flow with PKCE (S256),

    • ID tokens with email and email_verified, where email_verified is the boolean true. A string "true" counts as unverified.

    • In your provider, create an OIDC web application and register this redirect URI:

      https://sync.example.com/auth/callback/oidc

    • Note the issuer URL, client ID and client secret. Typical issuer URLs:

      Provider Issuer URL
      Okta https://example.okta.com/oauth2/default
      Keycloak https://<keycloak-host>/realms/<realm-name>
      Auth0 https://<your-tenant>.auth0.com/

    • Set these variables and restart:

      AUTH_PROVIDERS=local,oidc
OIDC_ISSUER=https://example.okta.com/oauth2/default
OIDC_CLIENT_ID=change-me
OIDC_CLIENT_SECRET=change-me
OIDC_DISPLAY_NAME=Okta
OIDC_ALLOWED_EMAIL_DOMAINS=example.com

    OIDC_ISSUER must use https. The button reads Continue with followed by OIDC_DISPLAY_NAME.

    Set OIDC_ALLOWED_EMAIL_DOMAINS to the domains you control. A generic provider might assert a verified email for a domain it doesn't own, and this list limits which emails can link to an account or sign up. Matching is exact: a subdomain isn't covered.

    You can list several providers at once, for example AUTH_PROVIDERS=local,google,oidc. The sign-in page shows one button per provider.

    Limit password sign-in¶

    Once SSO works, set:

    AUTH_LOCAL_LOGIN=admins

    This is the recommended setting with SSO. Only admins can still sign in with a password, as a break-glass path. Everyone else uses the provider button. A non-admin's correct password is refused.

    AUTH_LOCAL_LOGIN=off removes the password form entirely.

    The create-admin command and admin-issued set-password links keep working in every mode, including off.

    How accounts are matched¶

    People sign in through SSO with an account that already exists in AlgoBridge:

    • Invited users are matched by verified email on their first SSO sign-in. Invite them on the Users page first.
    • Existing password accounts with the same verified email are linked on the first SSO sign-in from that provider, including accounts with two-step verification on. After that, the account accepts either way of signing in. SSO sign-ins never ask for a two-step code: the provider's own sign-in security stands in for it.
    • Just-in-time sign-up: if the person has no account and their email domain is in AUTH_ALLOWED_DOMAINS, AlgoBridge creates one with the viewer role.

    Warning

    If you have password accounts you don't want linked to SSO, disable or rename them before you turn a provider on.

    Troubleshooting¶

    These notices appear on the sign-in page.

    That account is not part of the organization this console accepts.

    Google: the hd claim was missing or didn't match GOOGLE_HOSTED_DOMAIN, usually a personal account. Microsoft: the token's tenant didn't match MICROSOFT_TENANT_ID. Generic OIDC: the email domain isn't in OIDC_ALLOWED_EMAIL_DOMAINS.

    Your identity provider did not confirm your email address…

    The ID token had no verified email. For Microsoft, add the email and xms_edov optional claims. For generic OIDC, request the email scope and check that the provider sends email_verified as a boolean.

    Your account is not set up in AlgoBridge yet.

    No user is invited with this email, and AUTH_ALLOWED_DOMAINS doesn't cover it. An admin can invite the person on the Users page.

    This account is disabled.

    An admin can enable the account on the Users page.

    This AlgoBridge account is already linked to a different sign-in from that provider.

    The AlgoBridge account is already tied to another identity from the same provider. An admin has to resolve this; unlinking isn't self-service yet.

    Sign-in with your identity provider did not complete.

    The provider returned an error, for example because consent was denied. Try again, and check the application settings in the provider if it persists.

    Your sign-in took too long or was already used.

    More than 10 minutes passed, or the sign-in was already completed once. Click the provider button again.

    Your identity provider could not be reached.

    AlgoBridge couldn't reach the provider's discovery or token endpoint. Wait and try again. Admins can still sign in with a password unless AUTH_LOCAL_LOGIN=off.

    The container refuses to start

    A provider is listed in AUTH_PROVIDERS without all its variables, MICROSOFT_TENANT_ID isn't a GUID, OIDC_ISSUER isn't https, or AUTH_LOCAL_LOGIN conflicts with AUTH_PROVIDERS. The startup error names the variable.
