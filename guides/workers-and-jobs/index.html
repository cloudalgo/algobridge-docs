    Run workers and jobs¶

    This guide shows you how to split the console and the sync work into separate containers, scale workers, stop them safely, and read the Jobs & workers page when something gets stuck.

    All background work, such as sync ticks, loads, the watchdog and cleanup, runs as jobs in PostgreSQL. The jobs live in the algobridge_jobs schema of the platform database. There is no Redis, broker or external queue to run. See Architecture.

    Before you start¶

    • AlgoBridge is installed and the platform database is migrated. See Install.
    • You can set environment variables and restart containers in your runtime.

    Choose a role for each container¶

    APP_ROLE decides what a container does:

    APP_ROLE Serves the console Runs jobs
    all Yes Yes
    web Yes No
    worker No Yes

    A single all container is enough for most installs. Run web and worker containers separately when you want to scale the console and the sync work independently, or keep sync running while you restart the console.

    Every container, whatever its role, needs the same DATABASE_URL and the same ENCRYPTION_KEY.

    Split web and worker¶

    1. Run the migrate role once for the version you're deploying:

      docker compose -f deploy/docker-compose.yml run --rm app migrate

      Outside Docker, run node dist/cli/migrate.js. It applies the platform migrations and installs or upgrades the job schema. It is safe to run more than once.

    2. Start one or more containers with APP_ROLE=web, behind your load balancer.

    3. Start one or more containers with APP_ROLE=worker. Workers need outbound access to Salesforce and the client database, but no inbound traffic.
    4. Open Instance → Jobs & workers and check that each worker appears under Workers with its role.

    A container that starts before migrate has run refuses to boot with The job schema is not installed. Run the migrate role first.

    Scale workers¶

    Workers share the queues. Each sync key runs on one worker at a time, so adding workers spreads keys across them rather than running a key twice. If a worker dies mid-job, another worker takes the job over, usually within 16 to 25 seconds.

    Each container polls the platform database every 2 seconds. That costs a few cheap queries per container, so run as many workers as the sync load needs and no more.

    Stop a container safely¶

    On SIGTERM, a worker stops taking new jobs and lets the running ones finish, for up to 30 seconds. It then marks itself stopped and closes its connections.

    Give every container a stop timeout longer than 30 seconds, so your runtime never kills it first:

    services:
  app:
    stop_grace_period: 45s

    The file in deploy/docker-compose.yml already sets this. Keep it when you copy the file. The Compose default is 10 seconds.

    docker stop --time 45 <container>

    The default is 10 seconds.

    spec:
  terminationGracePeriodSeconds: 45

    The default is 30 seconds, exactly the drain deadline, so set it explicitly.

    On any other runtime, set its stop or drain timeout to 45 seconds or more.

    If a container is killed before it finishes draining, its jobs are taken over once their heartbeat lapses, and its worker row shows as online until it goes stale.

    Upgrade¶

    1. Run migrate for the new version.
    2. Roll out the web and worker containers.

    Workers drain and hand over as described above, so a rolling restart doesn't lose work.

    Read the Jobs & workers page¶

    Instance → Jobs & workers shows:

    • Workers: each worker's role, host, start time, last seen time and jobs in flight.
    • Queues: per-queue counts of waiting, active and retrying jobs, completed and failed in the last 24 hours, and the queue's state.
    • Jobs: the job list, filtered by state (waiting, active, retrying, failed, completed, cancelled) and queue, with each job's key, retries and last error.
    • Engine warnings from the last 24 hours.

    The page refreshes every 5 seconds while the tab is visible. Job payloads are never shown.

    Everyone can see the page. Members and admins can also retry, cancel, redrive and dismiss.

    Queue states¶

    State Meaning
    healthy Jobs are being picked up on time.
    backlog Some ready jobs have waited more than 30 seconds.
    failing A job in this queue failed in the last 24 hours.
    idle No jobs in the last 24 hours.
    dead letter The dead letter queue holds jobs.

    Notices in the navigation¶

    Every page marks Jobs & workers in the navigation when something needs attention:

    • No worker is running. Sync is paused. with a ! badge: a worker has run before, and none has checked in for 30 seconds. Start a worker or all container.
    • N jobs in dead letter: jobs used up their retries. Open the page, read the last error, fix the cause, then redrive.

    Handle dead letter jobs¶

    A sync tick that fails five times moves to the dead letter queue. Meanwhile, the watchdog runs once a minute and restarts any sync key that has no queued tick, so sync resumes before anyone acts.

    1. Open Instance → Jobs & workers and read the Last error of the dead letter jobs.
    2. Fix the cause, for example a revoked Salesforce token or a missing database privilege.
    3. Click Redrive on the queue and confirm with Redrive jobs. The jobs go back to their original queues.
    4. If the notice says some jobs were left, their sync key is already queued or running again. Click Dismiss and confirm with Dismiss jobs. Dismissed jobs are cancelled and kept, with their last error, under the cancelled state until retention removes them.

    A sync key that fails with a configuration or authentication error isn't retried as usual. The watchdog restarts it within a minute, so it retries about once a minute until you fix the problem.

    Retention¶

    • Completed and failed jobs are kept for 14 days, then deleted.
    • Worker rows silent for an hour are pruned hourly. The most recent one is always kept.
    • Salesforce API usage rows older than 30 days are pruned hourly.

    Troubleshooting¶

    The job schema is not installed. Run the migrate role first.

    Run migrate for this version, then start the container again.

    No worker is running. Sync is paused.

    No worker or all container has checked in for 30 seconds. Start one, and check its logs if it exits at boot.

    Another job for that key is already queued or running

    You tried to retry or redrive a job whose sync key already has a job, usually because the watchdog restarted it. Dismiss the old job instead.

    A worker still shows as online after it stopped

    It was killed before it could mark itself stopped. Its jobs are taken over once their heartbeat lapses, and the row goes stale. Raise the container's stop timeout to 45 seconds.

    The same error repeats about once a minute

    A configuration or authentication error is being retried by the watchdog. Read the error on the page or in the Live log and fix the cause, for example reconnecting Salesforce.
