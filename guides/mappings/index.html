    Create mappings¶

    A mapping syncs one Salesforce object with one PostgreSQL table. This guide shows you how to choose the object and its fields, create the table, run the initial load, and reload a table when you need a fresh copy.

    Before you start¶

    • Salesforce is connected and the client database is connected. Until both are, Sync → Mappings shows Connect Salesforce and PostgreSQL first.
    • Your user has the member or admin role. See Users and roles.
    • The database role can create the target schema and use hstore. See Required privileges.

    Step 1: Check the mapping settings¶

    The Settings panel on Sync → Mappings applies to every mapping.

    • Target schema: the PostgreSQL schema AlgoBridge creates tables in. The default is algobridge. You can change it only until the first mapping exists. It must be a valid lowercase identifier (letters, digits and underscores, up to 63 characters) and can't be public, information_schema or start with pg_.
    • Write algorithm: how changes from PostgreSQL are sent to Salesforce. Ordered Writes (recommended) sends captured changes in order, one at a time, so a failed insert holds back only that record and rows that reference it. Merged Writes merges several changes to one record before sending, and sends parents ahead of children. See PostgreSQL to Salesforce.

    Click Save after changing either.

    Step 2: Choose an object¶

    1. Click New mapping.
    2. Search the list of objects, then click Choose on the one you want.

    The list shows objects that can be queried and replicated, as of the time shown. Click Refresh if you've just created an object in Salesforce. Big objects (__b), platform events (__e) and external objects (__x) aren't listed. An object without a SystemModstamp field is shown as one that can't be synced, because AlgoBridge uses that field to find changed records.

    Step 3: Set direction and conflicts¶

    • Direction:
      • Read-only (the default): Salesforce changes sync to PostgreSQL. PostgreSQL never writes back.
      • Read-write: changes also flow from PostgreSQL to Salesforce.
    • Conflict policy, for read-write mappings only: Salesforce wins (the default), PostgreSQL wins, or Latest change wins. See Conflicts.
    • Poll interval: set the fastest and slowest interval, between 2 and 60 minutes. The defaults are 5 and 30. While the object is quiet, the interval doubles after each poll that finds nothing, up to the slowest. A poll that finds a change resets it to the fastest.
    • External ID: for a read-write mapping, choose a Salesforce field that is marked both External ID and Unique. AlgoBridge uses it to match rows inserted in PostgreSQL to records, so a retried insert can't create a duplicate. Leaving it at None works, but the editor warns you about the risk.

    Step 4: Choose fields¶

    The fields table lists each field's label, API name, Salesforce type and the PostgreSQL column type it becomes. Tick Sync for each field you want, and tick Indexed to add an index on its column.

    • Id becomes the sfid column. Id and SystemModstamp are always synced and can't be unticked. IsDeleted is added for you.
    • CreatedDate and Name are ticked by default.
    • Column names are the field's API name in lowercase, for example billingcity or invoice_total__c.
    • For a lookup, you can sync a field of the related record through its relationship. The column is named <relationship>__r__<field>, for example account__r__external_id__c. Polymorphic lookups don't offer this.
    • Column names longer than 63 bytes, a column named id, and any name starting with algobridge_ are refused.

    Field types¶

    Salesforce type PostgreSQL type
    id, reference varchar(18)
    string, url, email, phone, encryptedstring varchar(length)
    picklist varchar(255)
    combobox varchar(length)
    multipicklist varchar(4099)
    textarea varchar(length) under 256, otherwise text
    boolean boolean
    int integer
    long bigint
    double, currency, percent numeric(precision, scale)
    date date
    datetime timestamptz
    time time
    anyType text

    Compound fields (address, location) and base64 fields can't be selected. Sync their component fields instead, such as BillingCity.

    What is not synced¶

    Formula fields are not synced. The editor lists them greyed out as Formula field — not synced, and a mapping that includes one is refused. Salesforce doesn't mark a record changed when only a formula's inputs change, so no polling source can keep a formula column correct. Compute the value in PostgreSQL instead, for example with a view or a generated column over the synced input fields.

    The editor also warns you about:

    • more than 100 fields on one mapping,
    • encrypted fields, which may arrive masked if the integration user can't see them unmasked,
    • a lookup whose target object isn't mapped,
    • fields that changed in Salesforce since the mapping was saved, which are flagged Removed from Salesforce when they were deleted.

    Step 5: Save, then apply¶

    1. Click Create mapping, or Save changes on an existing mapping. Saving changes nothing in your database.
    2. Review the Apply panel. It lists the exact statements AlgoBridge will run.
    3. Click Create table for a new mapping, or Apply changes for an edit.

    A worker runs the statements in one transaction: if any of them fails, none of them stick, and the mapping shows failed with the statement that failed.

    For every mapping, applying creates:

    • the target schema, if it doesn't exist,
    • the table, with a unique index on sfid, a unique index on the External ID column, and an index on each Indexed column.

    For a read-write mapping, it also creates:

    • the hstore extension,
    • the change log table algobridge_change_log, and an archive kept for 30 days,
    • the trigger function algobridge_capture_change() and a trigger algobridge_capture on the table,
    • the status columns algobridge_lastop and algobridge_err.

    Applying never drops or recreates a table, and never drops a column. A type change that would narrow a column is refused.

    Mapping states¶

    State Meaning
    draft Saved, not applied yet.
    provisioning Apply is running.
    active Syncing.
    paused Sync is stopped for this mapping.
    failed The last apply failed. The panel shows why.

    Step 6: Watch the initial load¶

    When a mapping first becomes active, AlgoBridge loads every record of the object into the table.

    It first counts the records, then picks the cheaper way to read them:

    • REST queries cost one request per 2,000 records.
    • Bulk API 2.0 costs about 5 requests plus one per 50,000 records.

    Bulk is used only when it is strictly cheaper, so small objects load over REST. If Salesforce refuses a Bulk job, the load falls back to REST.

    The mapping list shows progress, such as Loading 42%, and the mapping's Load panel shows rows read and the transport chosen. If the org is close to its API limit, the load waits and shows Waiting for API budget.

    Adding fields to an active mapping works the same way: after you apply, the Load panel lists the new columns waiting to load and fills them from Salesforce.

    To stop a load, click Stop load. Stopping keeps what has been read so far, and the panel shows Table may be incomplete — run Reload to finish.

    Reload a table¶

    Reload empties the table and reads the whole object again. Use it after stopping a load, or when you want the table to match Salesforce exactly.

    1. Open the mapping and click Reload in the Load panel.
    2. The dialog shows how many rows the table holds. Type the table name to confirm.
    3. Click Reload table.

    Before you reload, know that:

    • Salesforce wins. Changes made in PostgreSQL that haven't been sent yet are discarded, and rows with no sfid (inserted in PostgreSQL but not yet in Salesforce) are lost.
    • AlgoBridge runs TRUNCATE … RESTART IDENTITY inside the job. It never drops the table.
    • If another table has a foreign key to this one, Reload is refused. AlgoBridge never truncates with CASCADE.

    Daily reconciliation¶

    Once a day, at the hour set by reconcile_hour_utc (03:00 UTC by default), AlgoBridge compares every mapping with Salesforce using one Bulk query per mapping, about 5 requests each. Salesforce wins, and records deleted in Salesforce are deleted from the table. The sweep is deferred while the budget governor is slowing or pausing sync.

    Remove fields or a mapping¶

    • Remove fields: untick them and save. The dialog Stop syncing these fields? reminds you that the columns and their data stay in PostgreSQL and simply stop being written. Click Stop syncing and save.
    • Delete a mapping: click Delete mapping. Choose Keep the table, or Drop the table and everything in it and type the table name to confirm.

    Troubleshooting¶

    Someone else changed this mapping. Reload to see their changes.

    Another user saved the mapping after you opened it. Reload the page, check their changes, and make yours again.

    Apply failed

    The panel shows the statement that failed. The usual cause is a missing privilege on the client database, or a schema that already holds other tables on the first apply. See Required privileges.

    Reload is refused because of a foreign key

    Another table references this one. Drop or defer the foreign key, reload, then restore it.

    The load stays on Waiting for API budget

    The org's API usage is above the governor's threshold. The load continues once usage falls. See API budget.

    A field I need is greyed out

    It is a formula field, a compound field, or a base64 field. See What is not synced.
