    Release notes¶

    AlgoBridge v2 is in development

    Version 2 has not been released yet. It is a ground-up redesign, and the features below are built and tested but not yet published as a release. Some features are still to come; see Still to come. Expect changes before the first release.

    This page lists what has been built so far, in the order it was built, newest first. Dates are when the work joined the main branch.

    Change notifier¶

    2026-10-06

    • Push notifications from Salesforce. Record-triggered Flows tell AlgoBridge which objects changed, so it learns about changes without spending API calls. Notifications carry object names only, never record data. See Change notifier.
    • One-click pairing between the instance and the org, at a cost of 2 API calls, with key rotation and an instant revoke.
    • Signed requests. Every notification is signed and checked for key, org, timestamp, replay and rate. Repeated failed requests open an alert.
    • A slow fallback poll, hourly by default, catches anything a notification missed.
    • Your own saves are ignored. Changes made by AlgoBridge's integration user do not trigger notifications, so synced writes are not echoed back.
    • Fair to your org. The notifier leaves 1% of the org's daily asynchronous Apex allowance untouched.

    In this version you add the Flows by hand; see Apex bundle.

    Apex probe and change sources¶

    2026-10-05

    • The Apex bundle. A small, read-only Apex package you can deploy to your org from the console. It answers "has anything changed?" for up to 90 objects in one API call, against 5 per call without it.
    • Choose your change source: Composite (the default, nothing to install), Apex probe or change notifier. AlgoBridge verifies your choice before saving it, re-checks it daily, and falls back with an alert if it stops working. See Change sources.

    Live log¶

    2026-10-03

    • A real-time view of every process's log lines in the console, for administrators. Follow, pause, filter and copy. Nothing is stored; the log streams only while someone is watching. See Live log.
    • Clearer SSO refusals. When an identity provider refuses a sign-in, the log now records the provider's error code.

    Initial load, Reload and the daily sweep¶

    2026-09-25

    • Initial load of every record when you activate a mapping, over REST or Bulk API, whichever costs fewer calls, with progress on the console.
    • Reload empties a table and loads it again. You confirm it by typing the table name.
    • Daily reconciliation sweep removes rows Salesforce no longer has and repairs rows that differ. It refuses to delete a large share of a table at once.
    • Outbound sends on a latency bound: a batch goes when 200 changes are waiting or the oldest has waited the maximum wait.
    • Formula fields are blocked from sync, because polling cannot keep them correct.

    API budget governor and adaptive intervals¶

    2026-09-21

    • Soft and hard thresholds for the org's API usage. Above the soft threshold AlgoBridge slows down; above the hard threshold it pauses Salesforce calls, while changes keep queuing. See API budget.
    • Adaptive poll intervals. A quiet object is polled less often, and a busy one returns to its minimum interval.

    Salesforce to PostgreSQL sync¶

    2026-09-21

    • Change probes that check 5 objects per API call before reading anything.
    • Fetch and apply of changed records, matched on sfid and then on External ID, including deletes.
    • Conflict policies per mapping: sf_wins, pg_wins and latest_wins. See Conflicts.

    PostgreSQL to Salesforce sync, Bulk API and Activity¶

    2026-09-21

    • Writes to Salesforce over SOAP, 200 records per call, sending only changed fields, with the new sfid written back to your row.
    • Bulk API v2 for runs of 2,000 records or more.
    • Retries with backoff for rejected changes; failures are parked rather than lost.
    • The Activity screen: every change in both directions, with filters, record detail and Salesforce's error text. Retry or discard a failed change, or retry all failures.

    Provisioning¶

    2026-09-19

    • Tables built for you. AlgoBridge creates and extends mapped tables, the change log and the capture trigger in your database.
    • Additive changes only. It never drops or recreates a table, and it refuses a change that would narrow a column.
    • You stay in control. Every change is shown as a diff and runs only when you press Apply. A preflight check names any missing database grant.

    Mappings¶

    2026-09-18

    • Map Salesforce objects to tables: choose fields, set direction (read-only or read-write), pick an External ID, add reference fields.
    • Choose a write algorithm: Ordered or Merged.

    Job runner¶

    2026-09-15

    • Background jobs coordinated entirely in PostgreSQL, with a worker registry, automatic takeover when a worker stops, and a watchdog that restarts stalled schedules.
    • The Jobs and workers screen. See Workers and jobs.

    Salesforce connection¶

    2026-09-15

    • Connect your org through an External Client App, using OAuth with PKCE against your My Domain. Tokens are stored encrypted.
    • API usage at a glance. The connection screen shows the org's API usage and AlgoBridge's own share. See Salesforce connection.

    Client database connection¶

    2026-09-14

    • Connect your PostgreSQL from the console or with CLIENT_DATABASE_URL. The connection string is stored encrypted. See Client database.
    • Encrypted secrets with key rotation, through the rotate-encryption-key command.
    • A setup checklist on the dashboard.

    Single sign-on, form protection and user management¶

    2026-09-14

    • Single sign-on through OpenID Connect, with presets for Google Workspace and Microsoft Entra ID and a generic option for other providers. Optional sign-up by email domain, and a setting to require SSO. See Single sign-on.
    • Every form is protected by a signed token and a one-time key, so forged and double submissions are refused.
    • User management: invitations, role changes, disabling users and admin-issued password-reset links, with optional email over SMTP. See Users and roles.

    Foundation, sign-in and console shell¶

    2026-09-13

    • One container image that runs as console, worker or both, with health endpoints and a migrate command.
    • Local sign-in with argon2id passwords, optional two-step verification and account lockout.
    • Three roles (viewer, member, admin), with every route denied unless it names the permission it needs.
    • The console shell and the create-admin command for the first administrator.

    Still to come¶

    Planned, and not in the current build:

    • Automatic notifier Flows and a daily check of them, plus mutual TLS and an IP allow-list for the notify endpoint.
    • Alerts on their own screen and by email.
    • Webhooks for sync events.
    • A REST API (/api/v1) with access tokens.
    • An audit log of console actions.
    • A settings screen for instance settings.

    Before the first release, single sign-on will be checked against real Google Workspace and Microsoft Entra ID tenants, and the Apex bundle will be checked in a clean Salesforce org.
