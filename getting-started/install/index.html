    Install AlgoBridge¶

    In this page you run AlgoBridge and its platform database with Docker Compose, create the first admin, and check that the instance is healthy. The same image runs on any container platform; Compose is the reference deployment.

    Before you begin¶

    You need:

    • Docker with the Compose plugin (docker compose).
    • A copy of the AlgoBridge repository. The reference Compose file builds the image from it.
    • A host name for the console if anyone other than you will use it, such as sync.example.com, with TLS terminated in front of AlgoBridge.

    1. Look at the reference Compose file¶

    deploy/docker-compose.yml runs two services:

    Service What it is
    db PostgreSQL 16, the platform database, with a pgdata volume and a pg_isready health check.
    app AlgoBridge, built from the repository's Dockerfile, listening on port 3000. It starts once db is healthy.

    The app service starts with these settings:

    environment:
  DATABASE_URL: postgres://algobridge:change-me@db:5432/algobridge
  APP_ROLE: all
  MIGRATE_ON_BOOT: "true"
  PUBLIC_URL: http://localhost:3000
ports: ["3000:3000"]
stop_grace_period: 45s

    Everything else in the file is commented out: email, single sign-on, the client database, the encryption key and the Salesforce app credentials. The configuration reference explains each one.

    2. Set your values¶

    Edit deploy/docker-compose.yml before the first start.

    1. Change the database password. Replace change-me in both POSTGRES_PASSWORD and DATABASE_URL with the same strong password.
    2. Set PUBLIC_URL to the address people use to reach the console. Keep http://localhost:3000 for a trial on your own machine. Anywhere else it must be an https:// origin with no path, for example https://sync.example.com.

    3. Generate an encryption key and set it as ENCRYPTION_KEY:

      openssl rand -base64 32

      ENCRYPTION_KEY: <the generated value>

      AlgoBridge starts without it, but it encrypts the Salesforce tokens, stored connection URLs and two-step verification keys with it. Without it you cannot connect Salesforce, save a client database on the Connections screen, or turn on two-step verification.

    Keep the key safe

    Store ENCRYPTION_KEY with your other secrets. If you lose it, AlgoBridge cannot read the connections it stored, and you must connect them again. To change it later, see rotating the encryption key.

    Keep secrets out of the file

    For anything beyond a trial, put the passwords and keys in an .env file or your platform's secret store and reference them from Compose, rather than writing them into docker-compose.yml. AlgoBridge reads secrets only from environment variables.

    3. Build and start¶

    From the repository root:

    BUILD_COMMIT=$(git rev-parse HEAD) docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml up -d

    BUILD_COMMIT is optional. When set, the console's sidebar footer shows the short commit the image was built from.

    On start, the container's entrypoint runs the migrations first because MIGRATE_ON_BOOT is true, then starts the app. Follow the logs while it boots:

    docker compose -f deploy/docker-compose.yml logs -f app

    The migration prints applied: … (or no pending migrations) and job schema ready. Logs are structured lines on stdout.

    If a setting is wrong, the container exits at once with a single line that names every problem, for example:

    Invalid configuration — PUBLIC_URL: must be https unless the host is localhost (set ALLOW_INSECURE_PUBLIC_URL=true to accept plain http on a trusted network)

    Fix the value and run up -d again.

    Create the first admin¶

    AlgoBridge has no default account and no sign-up page. Create the first admin from the command line once the database is migrated:

    docker compose -f deploy/docker-compose.yml run --rm app create-admin --email you@example.com --name "Your Name"

    The command prints:

    Created admin you@example.com (invited).
Set-password link (shown once, valid 7 days): https://…
Open it to choose a password, then turn on two-factor authentication.
    1. Open the link and choose a password. The link works once and expires after 7 days.
    2. Sign in at your PUBLIC_URL.
    3. Open your Account page and turn on two-step verification. It is optional, and recommended for every admin.

    If the command says Platform database is not migrated — run migrate first, run:

    docker compose -f deploy/docker-compose.yml run --rm app migrate
    Lost the link, or locked out?
    • The email must not already belong to a user. If the link expired unused, run the command again with a different email, or have another admin issue a new link from the Users page.
    • If every admin is locked out, run create-admin with a new email, then issue reset links for the original accounts from Users.
    • create-admin and admin-issued set-password links work in every AUTH_LOCAL_LOGIN mode, including off. They are the break-glass path when single sign-on is misconfigured.
    • Outside Docker, run node dist/cli/create-admin.js --email … --name … with DATABASE_URL and PUBLIC_URL set.

    Without SMTP configured, invite and password-reset links for other users are shown to the admin once, to copy and send. To email them instead, set SMTP_URL and SMTP_FROM.

    Check health¶

    The app answers two unauthenticated endpoints on PORT:

    Endpoint Answers Use it for
    GET /healthz 200 {"status":"ok"} whenever the process is serving HTTP. Liveness.
    GET /readyz 200 {"status":"ready"} when the platform database answers within 2 seconds and has every migration this build expects. Otherwise 503 {"status":"unavailable"}, with "reason":"migrations_pending" when the database is behind the build. Readiness, load balancer health checks. 
    curl -i http://localhost:3000/readyz

    The image has its own HEALTHCHECK on /readyz: every 15 seconds, a 5-second timeout, 3 retries, and a 60-second start period that covers a migration on boot. It uses Node's own fetch, since the image has no curl or wget. docker compose ps shows the result.

    Choose an APP_ROLE¶

    One image, three roles:

    APP_ROLE Serves the console Runs jobs Typical use
    all (default) yes yes A single container. Enough for most installs.
    web yes no Scale the console separately, behind a load balancer.
    worker no yes Scale the sync work separately.

    All coordination goes through the platform database, so you can run several web and several worker containers against the same DATABASE_URL. Workers share the queues, and each mapping's sync runs on one worker at a time. If a worker dies mid-job, another takes the job over, usually within 16 to 25 seconds.

    Every role listens on PORT and answers /readyz. Every role needs the same environment, including ENCRYPTION_KEY.

    Sync needs a running worker

    With no worker or all container running, nothing syncs. The console then marks Jobs & workers with No worker is running. Sync is paused. See Workers and jobs.

    Migrations with more than one container¶

    MIGRATE_ON_BOOT=true is a convenience for a single container. When you run separate roles, run migrations as an explicit one-off step instead, and leave MIGRATE_ON_BOOT unset:

    docker run --rm -e DATABASE_URL=postgres://algobridge:change-me@db.example.com:5432/algobridge <image> migrate

    The migration takes a database lock, so two runs at once queue rather than collide, and it is safe to run more than once. A web or worker container that starts before migrations refuses to boot with a message telling you to run migrate.

    Stopping a container¶

    On SIGTERM, a worker stops taking new jobs and lets running ones finish for up to 30 seconds. Give the container more time than that, so it is never killed first:

    • Docker Compose: keep stop_grace_period: 45s from the reference file. The Compose default is 10 seconds.
    • docker stop: use docker stop --time 45.
    • Kubernetes: set terminationGracePeriodSeconds: 45. The default is 30.

    Upgrade¶

    1. Get the new version of the repository and build the image again.

    2. Run the migrations for the new version before any new web or worker container starts. With the reference Compose file, MIGRATE_ON_BOOT=true does this on start:

      BUILD_COMMIT=$(git rev-parse HEAD) docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml up -d

      With separate roles, run migrate as a one-off step first, then roll out the containers.

    3. Check /readyz on the new containers.

    A container refuses to start against a platform database that is behind its build, with a message that lists the pending migrations. The reverse is allowed: a container older than the database starts and logs a warning, so a rollback or a rolling upgrade does not cause an outage.

    A new version may also change the capture trigger AlgoBridge installs in your client database. In that case each affected mapping's Apply panel offers to reinstall change capture; nothing in your database changes until you click it.
